# Геозоны трасс

## Что было не так

У геозоны хранилась одна точка `road_lat`/`road_lon` — «середина» коридора, — и
расстояние до дороги считалось до неё. Зона срабатывала, если стадо ближе
`buffer_km * 1.5` = 7.5 км от этой точки.

Для трассы А-1 (Астана — Алматы, ~1000 км по осевой) это означало, что зона
работала на отрезке около 15 км, то есть примерно на **1.5% своей длины**:

| Где стадо | До «точки дороги» | Алерт |
|---|---|---|
| Астана, начало трассы | 110 км | нет |
| Караганда, прямо на трассе | 197 км | нет |
| Алматы, конец трассы | 933 км | нет |
| рядом с самой точкой | 2.6 км | да |

## Как сейчас

`geozones.road_geometry` хранит осевую линию как JSON `[[lat, lon], ...]`, а
расстояние считается до ломаной (`distance_to_polyline_km`). То же стадо под
Карагандой теперь даёт `critical` с расстоянием 0.00 км.

Bounding box больше не задаётся руками: он вычисляется из геометрии плюс запас
`buffer_km + BBOX_MARGIN_KM`, поэтому не может разойтись с самой дорогой.

Та же математика продублирована на клиенте (`src/utils/geo.ts`) — там она нужна
для отметок скота у дороги. Реализации сверены: на контрольных точках расходятся
меньше чем на 1e-9 км.

## Откуда берётся геометрия

`backend/app/data/roads.json`, поле `geometry_source`:

- **`waypoints`** — точки, по которым фронт рисует трассу на карте
  (`useRoutePolyline.STATIC_WAYPOINTS`). Приближение в 4–15 точек на трассу, но
  повторяет реальный ход дороги. Так заданы А-17, А-1, А-21, Е-40.
- **`midpoint`** — историческая одна точка из старого сида, реальной геометрии
  нет. Такие коридоры (Павлодар — Семей, Павлодар — Омск) работают ровно как
  раньше: `distance_to_polyline_km` для линии из одной точки вырождается в
  обычный haversine. Ждут нормальных данных.

## Как заменить на настоящую геометрию OSM

Waypoints — приближение. Настоящая осевая линия лежит в OpenStreetMap, трассы
Казахстана размечены тегом `ref` (`A-1`, `A-17`, `A-21`).

Запрос к Overpass API для одной трассы:

```
[out:json][timeout:60];
area["ISO3166-1"="KZ"][admin_level=2]->.kz;
way(area.kz)["highway"]["ref"="A-1"];
out geom;
```

Полученные `way` нужно склеить в одну линию по общим узлам, упорядочить и
проредить (алгоритм Дугласа — Пекера) — сотни тысяч точек в БД не нужны, для
расстояния до дороги хватает шага в несколько километров. Результат положить в
`roads.json` с `geometry_source: "osm"`.

Скрипт для этого пока не написан: в окружении, где велась работа, сетевая
политика закрывает `overpass-api.de`, а отдавать непроверенный код не хотелось.
Запрос выше проверяется вручную на <https://overpass-turbo.eu>.

## Пересев

Сид сопоставляет зоны по `slug` и обновляет существующие. Раньше он выходил,
если таблица не пуста, — правки данных до работающей базы не доезжали вовсе.
Зоны, которых больше нет в `roads.json`, не удаляются (на них могут ссылаться
алерты), а помечаются `is_active = false`.

Сид запускается в lifespan приложения, то есть на каждом старте. Отдельно:

```bash
cd backend && python -m app.seed
```

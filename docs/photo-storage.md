# Хранение фотографий инцидентов

## Что было не так

Фото приходило в base64 внутри запроса, уходило в модель на проверку и на этом
исчезало. Колонка `photo_url` не заполнялась никогда — при том, что и
`IncidentDetailScreen`, и `IncidentCard` её показывают: `photo_uri || photo_url`.

`photo_uri` — локальный файл на телефоне автора. То есть человек, отправивший
репорт, видел своё фото, а **все остальные не видели ничего**. Для приложения,
где водитель решает, верить ли сообщению «лошади на дороге», это заметная
потеря: фотография — самый убедительный аргумент.

## Выбор хранилища

| Вариант | Плюсы | Почему не он |
|---|---|---|
| Postgres (`bytea`) | ничего не поднимать, транзакционно | у Neon на бесплатном тарифе 0.5 ГБ на всю базу; раздача картинок через FastAPI съедала бы и без того скудный процесс Render |
| Диск Render | проще некуда | на бесплатном тарифе эфемерный, файлы исчезают при каждом деплое |
| AWS S3 | стандарт, всё документировано | исходящий трафик платный и растёт непредсказуемо ровно тогда, когда приложением начинают пользоваться |
| Supabase Storage | удобный API, CDN | ещё один сервис со своим засыпающим бесплатным тарифом; 1 ГБ |
| **Cloudflare R2** | **исходящий трафик бесплатный**, 10 ГБ бесплатно, API совместим с S3 | — |

**Выбран R2.** Решающим был исходящий трафик: нагрузка здесь — раздача картинок,
и каждый открытый инцидент это скачивание. У R2 egress бесплатный, у S3 — нет.
10 ГБ хватает примерно на 70 тысяч фото по 150 КБ.

Код ходит в хранилище обычным S3-клиентом, поэтому S3, MinIO или Backblaze B2
подключаются сменой одного `S3_ENDPOINT_URL` — выбор не запирает.

`boto3` добавляет 23 МБ к образу; для холодного старта Render это приемлемо,
а самописная подпись SigV4 стоила бы больше рисков, чем экономит места.

## Настройка

Хранилище **выключено, пока не заданы переменные**. Без них всё работает ровно
как раньше: фото проверяется моделью и не сохраняется.

1. Создать бакет в Cloudflare R2.
2. Открыть публичный доступ на чтение (домен `r2.dev` или свой CNAME).
3. Выпустить API-токен с правами на чтение и запись объектов.
4. Заполнить переменные — список в `backend/.env.example`, для прода
   в Render Dashboard (см. `render.yaml`).

Публичный бакет означает: у кого есть ссылка, тот видит фото. Имя объекта —
случайный UUID (`incidents/{id}/{uuid}.jpg`), поэтому перебором по номеру
инцидента чужие фото не вытащить.

## Что и когда сохраняется

Фото сохраняется, **если модель его не отвергла**. Различаются два случая:

- модель посмотрела и сказала «это не дорога» → не храним (заодно ограничивает
  использование бакета не по назначению);
- проверка не выполнялась — нет ключа OpenAI, ошибка API, таймаут → **храним**,
  решать будет сообщество через подтверждения.

Раньше оба случая выглядели одинаково (`verified: false`), поэтому в результат
проверки добавлен флаг `checked`.

## Приватность

- Клиент пережимает фото до 800 px через `ImageManipulator` перед отправкой.
  Перекодирование попутно **срезает EXIF**, включая GPS-координаты съёмки.
- Удаление данных пользователя (`DELETE /devices/{id}/data`) удаляет и фото.
  Ключи ищутся по префиксу `incidents/{id}/`, а не выводятся из URL: публичный
  адрес может смениться, и тогда старые фото стали бы неудаляемыми.

## Устойчивость

Загрузка не может уронить создание инцидента. Ошибки хранилища логируются, и
метка всё равно появляется на карте — просто без фотографии. Ретраи boto3
ограничены двумя попытками с короткими таймаутами, чтобы пользователь не ждал.

## Чего нет

- **Модерации.** Единственный фильтр — проверка моделью. Жалоб на фото и
  ручного удаления пока нет.
- **Срока хранения.** Фото закрытых инцидентов лежат вечно. При заметном объёме
  стоит завести правило жизненного цикла в R2 — например, удалять объекты
  инцидентов, закрытых больше полугода назад.
